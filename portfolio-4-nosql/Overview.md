## Overview

In the previous portfolio activities, the JPMorgan Chase case study was implemented using Oracle Database 19c. Customer data, account information, products, ledger records, transaction history, and other core banking functions because these datasets were modelled using a relational structure because these entities require strong integrity, clearly defined relationships, and transactional consistency. However, transaction events often contain additional information that varies according to the channel through which the transaction was performed.

For this portfolio, a NoSQL solution is introduced to address a different requirement: storing transaction event records generated from multiple banking channels such as mobile banking, internet banking, ATM transactions, and branch operations.

While all transactions share common information such as account number, customer reference, amount, currency, transaction date, and status, the additional information captured during processing may vary significantly depending on the channel being used. For example, a mobile banking transaction may record device information and beneficiary details, while an ATM transaction may record terminal information and location details.

Using a traditional relational approach would require a large number of optional columns or additional supporting tables to accommodate these differences. A document-oriented model provides a more suitable approach because each transaction can store its own contextual information without forcing every record to follow exactly the same structure. 

Core banking activities such as account maintenance, balance updates, and transaction processing continue to be managed within Oracle 19c. These operations require ACID-compliant transactions and strict enforcement of business rules. By contrast, compliance and forensic records often contain information that varies from one event to another. For example, a domestic transfer investigation may capture different attributes from an international payment review. Storing these records in a traditional relational structure can lead to large numbers of optional columns or additional supporting tables.

However, I noticed that not all data generated by the banking system fits naturally into a relational structure. As the JPMorgan Chase Nigeria case study expands to include AML monitoring, forensic auditing, and security investigations, the system must also handle data whose structure can vary between events.

During the design of the `AML_FORENSIC_TRAIL` table, I initially focused on capturing the information required to support auditability and AML monitoring, including customer identifiers, risk score changes, terminal information, user activity, and a detailed audit payload. As I developed the reporting and investigation requirements for the JPMorgan Chase Nigeria case study, it became clear that compliance teams would frequently search for specific transaction-related information rather than the audit payload itself. For example, an investigator may need to retrieve all alerts associated with a particular account, review activities linked to a transaction reference, or identify transactions above a certain value threshold.

In the current design, much of this information would likely be stored inside `AUDIT_PAYLOAD_CLOB`. While this approach preserves flexibility, it also makes searching and indexing more difficult.

To address this limitation, I expanded the design to include several additional attributes as structured columns:

- `ACCT_NUM`
- `TRAN_REF`
- `TRAN_AMT`
- `CRNCY_CODE`
- `EVENT_STATUS`

These attributes represent information that investigators and compliance officers are likely to query regularly. Storing them as dedicated columns allows indexes to be created and improves the efficiency of compliance reporting.

The `AUDIT_PAYLOAD_CLOB` column remains useful for storing event-specific information that may vary between transactions, such as network metadata, device information, investigation notes, or additional message details. This provides flexibility without sacrificing query performance for commonly accessed data.

MongoDB was selected for this implementation because it allows transaction events and their associated metadata to be stored together within a single document. This makes it possible to retrieve complete transaction-event information without joining multiple tables and allows new channel-specific attributes to be added without modifying the entire database structure.

The purpose of this portfolio is not to replace the Oracle banking database developed in earlier portfolios. Oracle remains the system of record for customer, account, and ledger information. MongoDB is used only to demonstrate how transaction-event data with varying attributes can be modelled, queried, indexed, and analysed using a document-based NoSQL approach.

## Objectives

The MongoDB implementation demonstrates how to:

1. Create a NoSQL database and collection for transaction events.
2. Store transaction records using a document model.
3. Query transaction records using account identifiers and transaction status.
4. Filter transaction records by date and transaction channel.
5. Use aggregation to summarise transaction activity.
6. Create indexes to support common query patterns.
7. Evaluate the suitability of a document-based model for transaction-event storage within the JPMorgan Chase case study.

---

## Expected Outcome

The expected outcome of this portfolio is to demonstrate that a document-oriented database can complement the existing Oracle implementation by providing a flexible method for storing and analysing transaction-event information that does not naturally fit into a fixed relational structure.

The implementation will provide practical evidence through MongoDB scripts, query results, indexing examples, and execution screenshots.
