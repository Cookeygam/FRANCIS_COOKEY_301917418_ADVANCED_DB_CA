# NoSQL Databases and Polyglot Persistence

In the previous portfolios, all data was stored within Oracle 19c using a fully relational database design. This approach was appropriate for customer records, account balances, transaction history, and other core banking functions because these datasets require strong consistency, clear relationships, and transactional integrity.

However, I noticed that not all data generated by the banking system fits naturally into a relational structure. As the JPMorgan Chase Nigeria case study expands to include AML monitoring, forensic auditing, and security investigations, the system must also handle data whose structure can vary between events.

During the design of the `AML_FORENSIC_TRAIL` table, I initially focused on capturing the information required to support auditability and AML monitoring, including customer identifiers, risk score changes, terminal information, user activity, and a detailed audit payload. As I developed the reporting and investigation requirements for the JPMorgan Chase Nigeria case study, it became clear that compliance teams would frequently search for specific transaction-related information rather than the audit payload itself. For example, an investigator may need to retrieve all alerts associated with a particular account, review activities linked to a transaction reference, or identify transactions above a certain value threshold.

In the current design, much of this information would likely be stored inside `AUDIT_PAYLOAD_CLOB`. While this approach preserves flexibility, it also makes searching and indexing more difficult.

To address this limitation, I expanded the design to include several additional attributes as structured columns:

- `ACCT_NUM`
- `TRAN_REF`
- `TRAN_AMT`
- `CRNCY_CODE`
- `EVENT_STATUS`

These attributes represent information that investigators and compliance officers are likely to query regularly. Storing them as dedicated columns allows indexes to be created and improves the efficiency of compliance reporting.

The `AUDIT_PAYLOAD_CLOB` column remains useful for storing event-specific information that may vary between transactions, such as network metadata, device information, investigation notes, or additional message details. This provides flexibility without sacrificing query performance for commonly accessed data.

This design decision reflects a balance between two competing requirements within the case study:

1. Maintaining efficient access to frequently queried compliance data.
2. Preserving the ability to capture detailed forensic information whose structure may change over time.

The limitations of storing highly variable audit data within a relational table also provide a practical motivation for the MongoDB implementation explored later in this portfolio. While Oracle remains the preferred platform for structured banking data, a document database may provide a more suitable solution for storing complex and evolving audit records.

The purpose of this portfolio is to investigate whether a document-oriented database can complement the existing Oracle environment. Rather than replacing Oracle, the objective is to identify which workloads are better suited to a NoSQL model and evaluate the benefits and limitations of storing data across multiple database platforms.

## Applying Polyglot Persistence to the Case Study

The database solution proposed in the earlier portfolios separates operational banking data from compliance and audit information.

Core banking activities such as account maintenance, balance updates, and transaction processing continue to be managed within Oracle 19c. These operations require ACID-compliant transactions and strict enforcement of business rules.
By contrast, compliance and forensic records often contain information that varies from one event to another. For example, a domestic transfer investigation may capture different attributes from an international payment review. Storing these records in a traditional relational structure can lead to large numbers of optional columns or additional supporting tables.

To satisfy the rigorous production criteria of our commercial banking engine, I have architected a hybrid polyglot data tier. This model isolates structured financial accounting from unpredictable compliance auditing streams:

```text
                 Banking Application
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
        ▼                                   ▼

      Oracle 19c                       MongoDB

  • Customer Records            • AML Audit Records
  • Account Balances            • Investigation/ Transaction Logs
  • Ledger Transactions         • Security Events
  • Corporate Accounts          • Variable JSON Payloads
```

## Oracle 19c: Core Banking Data

Oracle remains the primary database platform for the operational banking system.

Tables such as:

- `TRANSACT.GENERAL_ACCT_MAST_TABLE`
- `CUSTOMER.CORPORATE_CUSTOMER_MASTER`
- `CUSTOMER.RETAIL_CUSTOMER_MASTER`
- `TRANSACT.DAILY_TXN_DTL`

contain highly structured data and support the transaction-processing workflows developed in previous portfolios.

For example, balance deductions, account updates, and customer validation checks must all occur within controlled transactions. Oracle's support for constraints, foreign keys, row-level locking, and ACID transactions makes it suitable for these requirements. A failed transaction should never result in a partially updated account balance, making data consistency the highest priority for this part of the system.

### Workload Balancing Strategy

• The Relational Engine (Oracle 19c): Processes the core accounting ledger table GENERAL_ACCT_MAST_TABLE (GAM). Financial bookkeeping demands absolute schema rigidity, atomic multi-row mutations, and strict precision scales to guarantee balance sheet integrity during real-time clearing.

• The Document Engine (MongoDB Enterprise): Targets the payment_events collection within the portfolio_nosql database. This engine acts as our high-velocity streaming event store, capturing immediate transactional state updates across our digital channels (Web, Mobile, API gateways). Financial event payloads are inherently polymorphic: a web interface login registers basic transmission keys, whereas a corporate mobile connection appends deep device risk signals and nested application metadata snapshots. Capturing these attributes within Oracle 19c would require costly, continuous DDL schema updates or unindexed large text blocks (CLOB). Shifting this logging subsystem to MongoDB allows our framework to ingest multi-format messages natively as nested BSON objects, safeguarding the relational transactional core.
